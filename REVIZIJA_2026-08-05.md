## Резиме

**Стек:** Laravel 12, PHP 8.2+, Filament 4, Filament Shield 4, Spatie Permission 6, Spatie Activitylog 4, Livewire 3, lab404/laravel-impersonate, maatwebsite/excel.

**Домен:** евиденција конкурсних поступака за попуњавање радних места у државним органима. Подаци су изоловани **по органу** — де факто мулти-тенант систем, али без правог tenant механизма (Shield `tenant_model` је `null`).

**Општи утисак:** главни ресурс (`PodaciORadnomMestuResource`) је промишљено урађен — изолација по органу постоји у три слоја (`getEloquentQuery` → `Policy` → `Model::booted`), импресонација је read-only на Gate нивоу, аудит траг постоји, коментари објашњавају „зашто", а не „шта". То је изнад просека.

**Главни проблем:** та иста правила примењена су **само на један ресурс**. Корисници, Позивнице и Евиденција активности немају ништа од тога. Уз то: нула употребљивих тестова, нула индекса на најоптерећенијој табели, и сидер који убацује познату лозинку за Super Admin налог.

## 🔴 Критично

### 1. Вертикална ескалација привилегија кроз екран „Корисници"

**Локација:** `app/Filament/Resources/UserResource.php:66-72`, `app/Policies/UserPolicy.php`

```php
Select::make('roles')
    ->label('Улоге')
    ->multiple()
    ->relationship('roles', 'name')   // ← нуди СВЕ улоге, укључујући „Super Admin"
    ->preload()
    ->searchable()
    ->required(),
```

`UserPolicy` проверава само „да ли смеш да мењаш кориснике", никад **кога** смеш и **коју улогу** смеш да доделиш. Свако са дозволом `Update:User` (или `Create:User`) може себи или било коме доделити улогу `Super Admin` и тиме заобићи:

- целу изолацију по органу,
- ограничење „Обриши трајно" (`PodaciORadnomMestuPolicy::jeSuperAdmin`),
- страницу Подешавања (глобални 2FA прекидач),
- импресонацију.

**Исправка:**

```php
// UserResource::form()
Select::make('roles')
    ->relationship('roles', 'name', fn (Builder $q) => auth()->user()->isSuperAdmin()
        ? $q
        : $q->where('name', '!=', 'Super Admin'))
```

плус у `UserPolicy`:

```php
public function update(AuthUser $authUser, User $target): bool
{
    if (! $authUser->can('Update:User')) return false;
    if ($target->isSuperAdmin() && ! $authUser->isSuperAdmin()) return false;   // не дирај Super Admina
    if (! $authUser->isSuperAdmin() && $target->organ_id !== $authUser->organ_id) return false;
    return true;
}
```

Напомена: тренутне методе `UserPolicy` немају ни параметар модела (`view()`, `update()`, `delete()` примају само `$authUser`) — треба их проширити.

### 2. Нема изолације по органу на Корисницима, Позивницама и Евиденцији активности

| Ресурс | `getEloquentQuery()` | Последица |
|---|---|---|
| `PodaciORadnomMestuResource` (`:439-452`) | ✅ филтрира по органу | у реду |
| `UserResource` | ❌ **нема** | админ органа А види, мења и брише кориснике органа Б |
| `InvitationResource` | ❌ **нема** | види све позивнице; `Select organ_id` (`InvitationResource.php:59-63`) нуди **све органе** → може убацити новог корисника у туђи орган |
| `ActivityResource` | ❌ **нема** | види цео аудит лог: пуне diff-ове туђих записа, е-адресе и IP адресе свих корисника система |

Трећа ставка није само проблем ауторизације него и заштите података о личности — IP адресе и обрасци понашања корисника других органа су лични подаци.

**Исправка** (исти образац као на главном ресурсу):

```php
public static function getEloquentQuery(): Builder
{
    $query = parent::getEloquentQuery();

    if (auth()->user()?->isSuperAdmin()) {
        return $query;
    }

    return $query->where('organ_id', auth()->user()?->organ_id);
}
```

За `ActivityResource` филтрирање иде преко `causer` (корисници истог органа) или преко `subject` кад је субјект `PodaciORadnomMestu` са одговарајућим `organ`.

### 3. Сидер убацује познату лозинку у продукцију

**Локација:** `database/seeders/AdminUserSeeder.php:18-59`, позван из `database/seeders/DatabaseSeeder.php:21`

```php
$superAdmin = User::firstOrCreate(
    ['email' => 'admin@kprm.rs'],
    ['name' => 'Super Administrator', 'password' => Hash::make('password123')]

$superAdmin->syncRoles(['Super Admin']);
```

Плус `test.admin@kprm.rs` и `test.kadrovik@kprm.rs`, обоје `password123`.

2. Иницијалну лозинку узимати из `env('ADMIN_INITIAL_PASSWORD')` или је генерисати насумично и исписати једном у конзоли.
3. Тест налоге оградити: `if (app()->isProduction()) { return; }`.
4. **Проверити продукциону базу** — да ли `admin@kprm.rs`, `test.admin@kprm.rs`, `test.kadrovik@kprm.rs` постоје. Ако постоје → обрисати или ротирати лозинке одмах.

### 4. `RoleSeeder` додељује улози „Admin" готово све дозволе

**Локација:** `database/seeders/RoleSeeder.php:25`

```php
$adminPermissions = Permission::where('name', 'not like', '%.delete')->get();
$admin->syncPermissions($adminPermissions);
```

Тај филтер је писан за стари naming из `config/modules.php` (`users.delete`, `roles.delete`). Shield генерише дозволе у формату `Delete:User`, `ForceDeleteAny:PodaciORadnomMestu` (сепаратор `:`, pascal case — `config/filament-shield.php:permissions`). **Ниједна Shield дозвола не одговара обрасцу `%.delete`.**

Последица: ако се `RoleSeeder` покрене после Shield генерисања дозвола, улога „Admin" добија **све** Shield дозволе, укључујући `Delete:*`, `ForceDeleteAny:*` и `Update:User` → што уз налаз #1 значи практично Super Admin.

Исто важи за улогу „Kadrovik" (`%.view` не хвата ништа од Shield naming-а) — добија **нула** дозвола, што је „безбедан" али погрешан исход.

**Исправка:** експлицитна листа дозвола по улози, у Shield naming-у. Уз то обрисати паралелни, мртви систем дозвола (`config/modules.php` + `PermissionSeeder`) — два наименовања дозвола у истој бази трајно производе овакве грешке.

## 🟠 Високо

### 6. 2FA кôд се чува у бази у чистом облику

**Локација:** `app/Filament/Pages/Auth/Login.php:149-155`, `app/Filament/Pages/Auth/TwoFactorChallenge.php:118-135`

```php
$code = str_pad((string) random_int(0, 999999), 6, '0', STR_PAD_LEFT);
$user->update([
    'two_factor_code' => $code,                      // ← plaintext у users
    'two_factor_expires_at' => now()->addMinutes(10),
]);
```

Ко има читање базе (резервна копија, dump, DBA, будући SQL injection) — заобилази 2FA у потпуности. Уз то:

- **Истекао кôд остаје у бази неограничено** — брише се тек при успешној верификацији (`TwoFactorChallenge.php:132`). Ако корисник никад не заврши пријаву, кôд стоји.
- Провера истека иде **после** поређења кôда (`:118` па `:124`) — безазлено по себи, али логика „кôд тачан али истекао" оставља кôд активним за следећи покушај.
- Колона `users.two_factor_enabled` постоји, налази се у `$fillable` и `$casts`, али се **нигде не проверава** — важи само глобални прекидач из Подешавања. Мртво поље које обећава функционалност коју нема.
- Нема ограничења на број **слања** кодова (сваки успешан унос лозинке шаље мејл). Захтева тачне креденцијале, па је ризик низак, али је ипак вектор за пуњење сандучета.

**Исправка:**

- чувати `Hash::make($code)` (или HMAC са `APP_KEY`), поредити преко `Hash::check`;
- брисати кôд при провери истека;
- поштовати `two_factor_enabled` по кориснику или обрисати колону;
- размотрити TOTP (RFC 6238) као јачу опцију — е-пошта је најслабији други фактор.

### 7. Нема политике лозинки, ни начина да се корисник деактивира

- `app/Filament/Resources/UserResource.php:58-65` — поље лозинке има само `maxLength(191)`. **Администратор може поставити лозинку од једног знака.**
- `app/Filament/Pages/Auth/RegisterInvite.php:85` — `minLength(8)`, без сложености и без провере компромитованих лозинки.
- `app/Models/User.php:85-90` — `canAccessPanel()` враћа `true` за **свакога**:

```php
public function canAccessPanel(Panel $panel): bool
{
    return true;
}
```

Нема `is_active`, нема верификације е-поште. Запослени који напусти орган може се уклонити само брисањем налога — чиме се губи веза са аудит трагом (`activity_log.causer_id` остаје да виси).

**Исправка:**

```php
// AppServiceProvider::boot()
Password::defaults(fn () => Password::min(12)->letters()->mixedCase()->numbers()->uncompromised());
```

плус колона `users.is_active` (default `true`), провера у `canAccessPanel()`, и акција „Деактивирај" у `UserResource` уместо брисања.

### 8. Пријава зависи од спољног сервиса преко нешифрованог HTTP-а

**Локација:** `app/Listeners/CheckLoginLocation.php:64`

```php
$response = Http::timeout(5)->get("http://ip-api.com/json/{$ip}", [
    'fields' => 'status,country,countryCode,city,query',
]);
```

Три проблема:

1. **Нешифровани HTTP** ка трећој страни — одговор се може изменити у транзиту (додуше, ефекат је само лажно упозорење или изостанак упозорења).
2. **IP адресе корисника државног система се шаљу спољном сервису** без основа обраде — питање за ЗЗПЛ/ГДПР.
3. **Синхроно, у току пријаве** — до 5 секунди кашњења по пријави; мејл упозорења (`Mail::to()->send()`, `:79`) такође иде синхроно.

**Исправка:** локална GeoIP база (MaxMind GeoLite2, офлајн, месечно освежавање) или проста whitelist домаћих IP опсега. Ако баш мора спољни сервис — HTTPS, унутар `ShouldQueue` job-а, са прекидачем у `config/`.

### 10. Импресонација — солидна, али са две рупе

Read-only заштита је добро осмишљена и на два нивоа:

- `app/Providers/AppServiceProvider.php:41-61` — `Gate::before` враћа `false` за све мутационе способности током импресонације (и policy-стил и Shield-стил именовања);
- `app/Models/PodaciORadnomMestu.php:115-126` — сигурносна мрежа на нивоу модела (`saving`/`deleting`/`restoring`).

Рупе:

1. **Мрежа на нивоу модела постоји само на `PodaciORadnomMestu`.** `User`, `Invitation` и `Setting` је немају. Ослањају се искључиво на Gate, што значи да ће свака будућа акција која не пролази кроз policy (директан `Model::update()` у Livewire акцији, на пример) пробити read-only гаранцију без иједног упозорења.

2. **Улазак у импресонацију је GET рута без CSRF заштите** (`routes/web.php:18`) која мења стање сесије:

```php
Route::get('/impersonate/take/{id}', function (string $id) { ... })->name('impersonate');
```

CSRF-ом (обичан `<img src="...">` или линк у мејлу) Super Admin се може натерати да уђе у преглед одабраног корисника. Утицај је ограничен (режим је read-only, циљ не сме бити Super Admin), али је state-changing GET и остаје у аудиту као да га је Super Admin намерно покренуо.

**Исправка:**

- извући `blokirajAkoImpersonira` из `PodaciORadnomMestu::booted()` у заједнички trait `PreventsMutationWhileImpersonating` и прикачити на све моделе;
- импресонацију пребацити на POST са CSRF токеном, или додати `signed` middleware.

### 11. Недостају безбедносна заглавља и CSP

Нема ниједног од: `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Strict-Transport-Security`, `Permissions-Policy`.

Апликација има inline `<script>` и `<style>` кроз render hook-ове (`AdminPanelProvider.php:84-118`), па CSP тражи nonce приступ — није тривијално, али је изводљиво.

Уз то:

- `SESSION_ENCRYPT=false` (`.env.example`) — а сесије су у бази и садрже `password_hash_web` (`AppServiceProvider:67`);
- `SESSION_SECURE_COOKIE` није форсиран у продукцији;
- `same_site=lax` — Filament ради и са `strict`.

**Исправка:** middleware `SecurityHeaders` у глобалном web стеку + `SESSION_ENCRYPT=true`, `SESSION_SECURE_COOKIE=true`, `SESSION_SAME_SITE=strict` у продукцијском `.env`.

### 12. Ниједан индекс на најоптерећенијој табели

**Локација:** `database/migrations/2025_12_31_083647_create_podaci_o_radnom_mestu_table.php` и све накнадне

Табела `podaci_o_radnom_mestu` нема индекс ни на:

- `organ` — филтрира се у **сваком** упиту (`OrganFilterService::applyOrganFilter`),
- `datum_oglasavanja` — `whereYear` у свих 11 виџета и у филтеру табеле,
- `tip_konkursa` — сваки виџет,
- `deleted_at` — soft deletes,
- `unos_zavrsen`.

Нема ни страних кључева према шифарницима (`vrsta_organa`, `organ`, `zvanje`… су обични `integer`).

Контролна табла има **11 виџета**, сваки покреће бар један упит → 11+ full table scan-ова по учитавању странице.

```php
Schema::table('podaci_o_radnom_mestu', function (Blueprint $table) {
    $table->index('organ');
    $table->index(['organ', 'tip_konkursa', 'datum_oglasavanja'], 'idx_organ_tip_datum');
    $table->index('datum_oglasavanja');
    $table->index('deleted_at');
});
```

**Ово је највећи добитак по уложеном труду у целом извештају.**

### 15. Excel извоз: синхрон + N+1

**Локације:** `app/Filament/Resources/PodaciORadnomMestuResource/Pages/ListPodaciORadnomMestus.php:26-31`, `app/Exports/PodaciORadnomMestuExport.php:104-181`

`getEloquentQuery()` (`:443-450`) eager-loaduje шест релација, али `map()` користи још шест које **нису** у `with()`:

- `tipKonkursaRelation`
- `proveraPfkRelation`
- `izabraniKandidatRelation`
- `drugoplasiraniKandidatRelation`
- `razlogNeuspelogKonkursaRelation`
- `oblastiRada`

То је ~6 додатних упита по реду. На 5.000 редова ≈ **30.000 упита у једном синхроном HTTP захтеву** → PHP timeout.

**Исправка:** допунити `with()`, увести `ShouldQueue` + `WithChunkReading`, слати кориснику Filament нотификацију са линком за преузимање.

> Успут: поље `broj_usvojenih_zalbi_na_resenje_o_prijemu_u_radni_odnos` се уноси, чува и логује, али **није у извозу** (headings има `...o_odbacaju_prijave`, недостаје `...o_prijemu_u_radni_odnos`).

### 16. `Setting::get()` удара у базу при сваком позиву

**Локација:** `app/Models/Setting.php:14-18`

```php
public static function get(string $key, $default = null)
{
    $setting = static::where('key', $key)->first();   // упит сваки пут
    return $setting ? $setting->value : $default;
}
```

Позива се:

- при **свакој** пријави (`Login.php:124`),
- при **сваком blur-у** поља „Назив радног места" (`PodaciORadnomMestuResource.php:480`, због `live(onBlur: true)` на `:486`),
- у `Podesavanja::mount()`.

**Исправка:** `Cache::rememberForever("setting:{$key}", ...)` са `Cache::forget()` у `set()`.

### 17. Видео се сервира кроз PHP

**Локација:** `app/Http/Controllers/KorisnickoUputstvoController.php:29-34`

```php
return response()->file(Storage::disk('local')->path($this->videoPath));
```

`BinaryFileResponse` подржава Range захтеве (премотавање ради), али сваки гледалац држи **PHP-FPM worker заузет током целог преузимања** вишестотинамегабајтног фајла. Неколико истовремених гледалаца може исцрпети pool.

**Исправка:** `X-Accel-Redirect` (nginx) или `X-Sendfile` (Apache) — ауторизација остаје у PHP-у, пренос преузима веб сервер.

## 🔵 QA — стање и стратегија тестирања

### Тренутно стање: **нема тестова**

`tests/` садржи два Laravel скелет примера:

- `tests/Unit/ExampleTest.php` — `assertTrue(true)`
- `tests/Feature/ExampleTest.php` — **пада**: тражи `GET /` → 200, а Filament панел на путањи `''` неаутентификованог корисника редиректује на пријаву (302)

Уз то `phpunit.xml` користи `DB_CONNECTION=sqlite` / `:memory:`, а апликација MySQL синтаксу (`DATEDIFF`, `YEAR()`) — сваки будући тест контролне табле пуцао би из погрешног разлога.

Постоји само `UserFactory` — нема фабрика за `PodaciORadnomMestu` ни за шифарнике, што значи да прво писање теста подразумева и подизање тог слоја.

### Предлог тест стратегије, по вредности

**1. Ауторизација и изолација — највиши приоритет** (ту су највеће рупе, налази #1–#4):

- корисник органа А не види и не мења запис органа Б: листа, директан URL `/{record}/edit`, извоз, виџети контролне табле, евиденција активности;
- корисник без органа не види ништа (`OrganFilterService` враћа `whereRaw('1 = 0')`);
- носилац `Update:User` **не може** доделити улогу `Super Admin`;
- „Обриши трајно" враћа 403 свакоме осим Super Admin-у;
- позивница се не може издати за туђи орган.

**2. Импресонација:**

- сваки мутациони пут враћа 403 (create, edit, delete, force delete, toggle „Унос завршен", bulk акције);
- аудит запис настаје при уласку и изласку;
- излазак враћа прави идентитет **и не одјављује** — синхронизација `password_hash_web` (`AppServiceProvider:67,79`) је суптилна и лако се поквари при надоградњи пакета.

**3. Пријава и 2FA:**

- погрешан кôд, истекао кôд, поновна употреба кôда;
- rate limit на верификацији (5 покушаја) и на пријави (`rateLimit(5)`);
- директан приступ `/two-factor-challenge` без `2fa_user_id` у сесији;
- неуспешна пријава производи `Failed` догађај и у 2FA режиму (`Login.php:132-138` — намерно ручно окидање, вредно закључавања тестом).

**4. Позивнице:**

- истекла / искоришћена / непостојећа;
- дупли е-мејл (постојећи корисник, постојећа активна позивница);
- лимит од 20 на сат, укључујући понашање у великом batch-у (`ManageInvitations.php:56`).

**5. Доменска правила:**

- аутоматика `ishod_konkursa` (терминални статуси 1/2/3/5 vs. „У току" = 4, `PodaciORadnomMestu.php:155-165`);
- ланци датума (`makeDateField` + `dateChainLabels`);
- збирне провере (`sumValidationRule`);
- ћирилична валидација назива радног места са укљученим и искљученим подешавањем;
- `unos_zavrsen_by` / `unos_zavrsen_at` се уписују само из кода, никад из форме.

**6. Идеална мета за чист unit тест:**

`PodaciORadnomMestuResource::izracunajStarosnuStrukturu()` (`:230-292`) — чиста функција, без базе: границе 18/90 година, датуми после референтног, оба формата уноса (`дд.мм.гггг` и `гггг-мм-дд`), празан улаз, прескочене ставке.

**7. Извоз:**

- број колона у `map()` == број у `headings()` (тренутно 73 : 73, али без теста то траје до следеће измене);
- извоз поштује активне филтере и изолацију по органу.

### Алати

- **Pest 3** (или PHPUnit ако се остаје на постојећем), `RefreshDatabase` над **MySQL** тест базом — не sqlite;
- Filament `livewire()` helper-и за тестирање форми, табела и акција;
- фабрике за `PodaciORadnomMestu` и шифарнике.

### Циљ покривености

100% на `app/Policies/` и `app/Services/OrganFilterService.php`, ~70% на доменској логици. Остало по потреби — покривеност није сама себи циљ, али ове две области јесу.
